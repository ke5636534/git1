第 14.5 章 Step10 拥塞闭环：pacing → ν → 点/秒（复刻 Fig.14）

14.5.1 这个文件干什么

前面九章把"事件 → 3D 点"的算法链路跑通了。这一章回到论文 §6.4 提出的系统级卖点：当网络拥塞、传输带宽被压低时，系统应该自动调严滤波阈值 ν，少发一些点，把带宽让给更重要的信息——形成一条"拥塞信号 → 滤波 → 输出点/秒"的闭环。

本步 step10_congestion.py 不重算几何，而是在 10P 场景的流式流水线上，喂三种"合成拥塞算法 pacing 轨迹"，验证这条闭环逻辑本身成立：pacing 低 → ν 严 → 每窗口保留的点少 → 输出点/秒低；pacing 高 → 放全 → 点/秒高。三条曲线（pacing 与点/秒）应高度同向、几乎无滞后。

生活类比：空调温控

把网络想象成一个房间，pacing 是"室外有多热"（拥塞越狠，pacing 越低），ν 是空调的制冷档位（ν 越严 = 扔掉越多事件 = 越省带宽 = 制冷越猛），房间温度就是输出点/秒。室外越热（pacing↓），你就把空调开越猛（ν↑），室温（点/秒）自然跟着室外温度走——这就是"闭环跟随"。

论文原文（§6.4, page 9）

"when the pacing rate is less than 2 Mbps or 4 Mbps the filter threshold ν in the triangulation application is set more restrictively to 0.1 or 0.25, respectively" —— 即论文的控制器规则：pacing < 2 Mbps → ν 最严（s≤0.1）；< 4 Mbps → ν 中（s≤0.25）；否则 transmit all。Fig.14 画的是 CUBIC / BBR / COPA 三算法下，ν 与"triangulated event points per second"随时间的曲线，结论是点/秒大致跟随 pacing，连探测阶段也跟随。

差异 #12：本步不接真实 QUIC

这是和论文最大的偏离，必须写清楚：环境里没装 aioquic，也没有可控瓶颈链路（Windows 上没有 tc/netem），无法产生真实的 pacing rate / RTT / 丢包序列。因此用三条合成 pacing 轨迹代替 CUBIC/BBR/COPA 的真实输出。本步证明的是"给定一条 pacing 曲线，闭环输出的点/秒会跟随它"；至于"真机上 pacing 会长这样"这件事，本步没有证明——那属于 P12（真实 QUIC）。

14.5.5 反标定：把论文的 s 换算成我们的 ν′

这一段是全步最容易抄错的地方。论文的 ν 是"坏度门槛：越小越好，保留 s ≤ ν"；我们的 quality_scores 是"好度：越大越好，保留 q ≥ ν′"。方向相反，所以 0.1/0.25/0.5 这三个论文数字不能直接套到我们的 q 上——否则 ν′=0.1 会把几乎所有点都留下来（等于没过滤）。做法是在全场景 q 分布上取分位数，换算成"等保留率"的 q 阈值。

14.5.8 小结

  1. 本步验证的是闭环逻辑本身（pacing→ν→点/秒跟随），不是 CUBIC/BBR/COPA 的实现正确性，更不是 QUIC 协议——因为用合成 pacing 代替了真实网络（差异#12）。
  2. 论文的 ν 是"坏度门槛"，我们的 q 是"好度"，方向相反，所以 0.1/0.25/0.5 不能直接套，要按保留率反标定成 q 阈值。
  3. quality_scores 是 O(n²) 红线：整段只算一次（第 278 行），逐窗口只做 O(n) 比较，否则从秒级变几十分钟。
  4. 离散 q 的并列组会让"直接分位数"偏差到 7pp；用 ±12 邻域联合标定压到 ≤2pp（验收 c）。
  5. 为让 ν 三档都能被走到，三条 pacing 轨迹的排空下限被有意放宽（CUBIC 重置回 1、BBR 到 1.6、COPA 到 0.8 Mbps）——这是偏离论文数字、为验收服务的合理放大，须写明。
