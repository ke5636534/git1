## 已知差异与坑（写报告时必读）

### 坑#1：1207 个匹配点只聚出 148 簇，丢掉 88%
**不是参数错，是像素量化。** `Z = f·B/d` 里视差 d 只有整像素精度，1 px 的 d 抖动会让 Z 跳约 **1.2 cm**，本身超过 1 cm 聚类半径 → "同一粒子的两个采样点"经常凑不进同一个球，各自成单点被丢。
论文用真实 DAVIS346 + 亚像素/多事件融合才没这么惨。**这是简化模型与原文最大的口径差异。**

### 坑#2：指标评"簇心"，不评"轨迹点"
简化检测器太稀疏（991 帧里只有 135 帧有检测），连续漏检 12 步会把轨迹删光，用轨迹点评分会让指标虚低甚至为 0。
论文 §6.1 评的是**每帧重建点集**，所以 Step5 吃 Step3 的簇心。两者差一点点（Chamfer 6.73mm vs 6.55mm），因为跟踪点是卡尔曼平滑后的位置，噪声更小。

### 坑#3：ν=1.0 时 Prec 掉到 0
质量阈值拉满 → 所有点都被滤掉 → 重建集为空 → Prec 分母为 0 → 记 0。**属预期，不是 bug。**

### 坑#4：Chamfer 必须双向
式(7) 是 `½·(mean_{o∈O}d(o,R) + mean_{r∈R}d(r,O))`。
早期版本因三元运算符优先级写错，只算了单向（4.6mm）；修正后 6.55~6.73mm 才是对的。

### 坑#5：~~ν 的横轴方向跟论文是反的~~ ✅ 已销号（2026-10-21，审查发现A）
- **根因**：`match_and_triangulate` 把式(2) 分数 s 算完就丢，下游 `streaming.quality_scores`
  只好用局部密度当好度代理，方向与论文相反（q 越大越好、保留 q≥ν）。
- **修复**：匹配函数新增 `return_scores=True` 返回 s 列；ν 滤波全线改论文口径**保留 s ≤ ν**
  （run_all.pipeline / step6 / step9 / step10 同步）；step10 的 `_calibrate_nu` 反标定整体删除，
  三档 ν 直接用论文原值 0.1/0.25/1.0。
- **修后行为**：ν 0→0.1→0.25→0.5→1.0 保留点数 0→448→998→1027→1055（1P），
  "陡升后走平"形状与论文 Fig.12 同轴同向，操作点 s≤0.5 可直接对照。

### 坑#6：κ 扫描下 Cov 掉得比论文凶
论文 §6.4 原话：raw 点的 Cov/Prec 在 κ 很小时**仍然很高**，只有 trajectory 点 Cov 下降。
本项目 κ=0.2 时 Cov 掉到 **0.467**（3P 场景），比论文惨得多。原因＝**坑#1 + 坑#2 的叠加**：
我们评的是聚类后的簇心（每帧需 ≥2 点，`MIN_POINTS=2`），事件砍 80% 后大量帧凑不到 2 点，簇直接消失；
论文评的是三角测量出的 raw 点本身，没有 minPts 门槛。**这是评估对象不同，不是算法错。**

### 坑#7：κ 与 ν 不能"同丢弃率直接比优劣"
实测（3P）：κ=0.6 → Cov 0.982；ν 保留约 60% → Cov 0.903。同保留率下 **κ 保召回更好**；
但 ν 全程 Prec=1.000（κ 只有 0.98~0.99），**ν 保准确更好**。
⇒ 正确说法是"κ 降延迟的粗调、ν 保精度的细调"，**不是"质量过滤完胜"**（论文也没这么讲）。

### 坑#8：流式窗口必须带 ±150µs 回看，否则匹配凭空丢 39%
Step8 第一版按 `[a, b)` 硬切窗口后，1P 的匹配数从 **1184 掉到 725**（−39%）。
根因：仿真事件全部聚在步长网格上（`t ≈ k·10 ms`，直方图在 mod 0/9999 处有两个尖峰），
而窗口网格起点 `t0 = min(事件时间) = −14.2 µs`，**两者错开 14 µs** ⇒ 每个突发正好骑在窗口边界上，
左事件进窗口 k、右事件进 k+1，配对被切开。
修复：切窗口时左右各扩 `T_MAX_US`（150 µs），匹配后只保留落在 `[a,b)` 的输出点。
修复后**自检 100.0%**（流式累计 1184 / 1184、2376/2376、3550/3550、5959/5959、11734/11734）。
→ 这不是仿真特有的问题：任何"按窗口切事件再匹配"的实现都必须带回看缓冲，
   真实接收端本来就是持有最近 150 µs 事件才做匹配的。

### 坑#9：L_proc 只涨 5 倍，不是论文的三个数量级
| | 论文 §6.2 | 本项目 |
|---|---|---|
| 1P 事件率/相机 | 5×10³ ev/s | **746 ev/s** |
| 10P 事件率/相机 | 27×10³ ev/s | **1797 ev/s** |
| L_proc 中位数 1P→10P | 涨 ≈1000× | **×5.1**（0.357→1.817 ms） |
两条原因，都指向"简化实现"而非算法错：
1. **事件率低 7~15 倍**：仿真每粒子每步只发 1 个事件（≈100 ev/s·粒子），
   真实 DAVIS346 里一个粒子会扫过多个像素，单粒子就能产生数千 ev/s。
2. **匹配复杂度低**：本项目用 `searchsorted` 建时间索引（O(log n + k)）；
   论文的匹配循环是**逐事件线性扫描找最优**（近 O(n²)），事件一多就爆。
⇒ 这恰好从反面印证论文 §6.2 的诊断：**瓶颈在匹配循环的写法，不在传感器**。
  趋势方向一致（随粒子数增大而增大）、量级不可直接对照。

### 坑#10：κ 有两套口径，step6 和 step9 抽的地方不一样（重要）

### 坑#11：L_proc 计时抖动 ±15%，锚点比对必须留容差
同一个 κ=1.0 @10P，三次跑出 **1.817 / 2.058 / 1.873 ms**（中位）。
原因是 10 ms 窗口里单次匹配只有几百微秒，`perf_counter` 的进程调度抖动占比就上来了。
⇒ ① TC12 的锚点容差取 ±25% 不是为了"放宽"，是物理上就这么抖；
  ② 写报告给 L_proc 时**必须标"单次测量"**，不要当成稳定常数；
  ③ **P14 已落地（2026-10-20）**：`step8.measure` 每个 (粒子数, κ) 重复 `N_REPEAT=5` 趟，
     事件数据在固定 seed 下是确定性的、只有墙钟在抖，于是把 5 趟的 `l_proc` 样本**拼接**
     成一维数组再取中位，相当于对同一场景多测几遍取合并样本，把中位方差压约 √5；
     TC12 新增硬判据"每趟单独中位相对本 κ 的拼接中位偏离 ≤25%"，证明没有一趟被 CPU
     抖动带偏到离谱。实测 10P 5 趟 worst 偏离 ≈13%、ptp ≈20%，稳健化生效。

### 坑#13：~~贪心 argmin 允许同一右事件被多个左事件认领~~ ✅ 已销号（2026-10-21，审查发现F）

### 坑#14：`Track.confirmed` 硬编码 False 与 `CONFIRM_AFTER=1` 自相矛盾
现象：Step4 输出"34 条轨迹、**0 个点**"。
根因：构造时 `self.confirmed = False`，而 `track_trajectories` 只收 `if tr.confirmed`。只活一帧的轨迹（占多数）永远等不到第二次 update → 永不确认 → 全被过滤。等于把阈值偷偷改成 2。
修法：`self.confirmed = self.hits >= C.CONFIRM_AFTER`（现 track.py 第 21 行）。
教训：**阈值参数化后，所有用到它的地方都必须引用参数，不许出现"等价但更严"的硬编码。**

### 坑#15：`quality_scores` 是 O(n²)，扫阈值前必须只算一次
10P 有 11734 个匹配点，11 档 ν 各算一次 = `11 × 11734² ≈ 1.5×10⁹` 次距离，跑不动。
修法：`step9.nu_scan` 第 110 行先算一次 q，11 档只做 `np.sum(q >= nu)`（O(n)）。总代价降 11 倍。
推广：任何"同一份数据扫多个阈值"的实验，都要把与阈值无关的预处理提到循环外。

### 坑#17：式(2) 第三项"带符号 vs 取绝对值"的解读差异（2026-10-21，审查发现B）
